# 录屏引入方案（可行性分析 + 落地设计）

> 状态：**方案已论证，实施未开始**。
> 本文是**决策层 + 预研层**文档，记录 Media Foundation 录屏链路的实测证据与踩坑。
> 实施完成后应把其中的「模块落点 / 类型签名 / 坑位」并入 `实现契约.md`，本文降级为历史预研记录。
>
> 配套文档：`WeChat4-截图工具逆向规格书.md`（微信原实现逆向）、`实现契约.md`（实现准绳）、`../README.md`（开发手册）。

## 1. 结论

**可以做，且零新增依赖。**

技术路线：**WGC 持续抓帧 → BGRA→NV12 转换 → Media Foundation SinkWriter → H.264 → MP4 容器**。

整条链路已在本机端到端跑通，产物是**结构完整、可被外部解码器读取的真实 MP4**（判据见 §3）。

但有三件事**不能指望 MF 替我们做**，必须自己写：

| 必须自己做的 | 原因 |
|---|---|
| **BGRA→NV12 色彩转换** | MF 的 H.264 编码器**不吃 BGRA**，喂进去编码器一帧都不吐（§4.1） |
| **按墙钟的真实时间戳控帧率** | WGC 出帧速率 ≠ 编码帧率（静态桌面可能几秒才一帧），用帧号算 pts 会让静止画面"快进" |
| **收尾补帧** | 编码器流水线尾部不会被 `Flush` 冲出来，**每次录制固定丢最后 ~3 帧**（§4.4） |

被排除的方案：

| 方案 | 排除理由 |
|---|---|
| ffmpeg 子进程 | 要捆绑/依赖外部二进制，与项目「依赖克制」原则冲突（且本机 ffmpeg 不在 PATH） |
| WebRTC / 会议 SDK | 那是会议推流，不是本地录制，且引入重型依赖 |
| x264 / libx264 | 需要 C 编译器与构建链，破坏「纯 Rust + 预编译依赖」现状 |
| DXGI Desktop Duplication 直接编码 | 性能最好（零拷贝），但代码量大（DXGI 1.2 / `DXGI_ERROR_ACCESS_LOST` / 多输出适配），**留作 M4 性能优化**，不在首版 |

## 3. 可行性验证（判据：外部可证伪）

### 3.1 验证方法

**不接受"API 调用没报错"作为成功判据。** 每一步都用外部工具复核：

1. 探针产出 `.mp4` 文件；
2. `ffprobe` 读流信息（编码器 / 尺寸 / 帧率 / 帧数 / 时长 / 容器 brand）；
3. `ffmpeg` 实际解码（`-count_frames` 统计**真实解码帧数**，而不是看 `stsz` 里写了多少）。

本机 `ffprobe` 路径：`D:\ffmpeg-9.0.1-essentials_build\ffmpeg-9.0.1-essentials_build\bin\ffprobe.exe`。

### 3.2 实测结果

| 项 | 结果 |
|---|---|
| 编码器枚举（`MFTEnumEx`，GUID `MFT_CATEGORY_VIDEO_ENCODER`） | 软件 SYNCMFT **7** 个 / 硬件 HARDWARE **11** 个 |
| 端到端写 H.264 MP4 | ✅ 产物 4,784,378 字节 |
| `ffprobe` 复核 | `codec_name=h264` / `profile=Constrained Baseline` / `320x240` / `pix_fmt=yuv420p` / `avg_frame_rate=30/1` / `nb_frames=297` / `duration=9.899967` |
| 容器 | `format_name=mov,mp4,m4a...`，`major_brand=mp42`，`compatible_brands=mp41isom` |
| `ffmpeg` 实际解码帧数 | 与 `nb_frames` 一致（297），首帧 `pts=0.000000`，末帧 `pts=9.866667` |
| 码率控制 | 目标 4 Mbps → 实测 3.83 Mbps（误差 <5%） |

## 4. Media Foundation 踩坑清单

以下每条都是本机实测得出，**任何一条写错都会让整条链断掉**。

### 4.1 输入必须是 NV12，不能是 BGRA

喂 `MFVideoFormat_RGB32`（内存序 B,G,R,A）：

| 调用 | 结果 |
|---|---|
| `SetInputMediaType` | ✅ **成功**（类型检查通过，容易误判为可行） |
| `WriteSample` | ✅ 成功 |
| `Flush` | ✅ 成功 |
| `Finalize` | ❌ `0xC00D4A44`「操作失败，因为接收器未处理任何示例」 |

编码器**一帧都没吐**。⇒ **BGRA→NV12 必须自己写**，MF 不会自动插色彩转换器。

### 4.2 码率必须显式设，且要放在**输出**媒体类型上

| 做法 | 结果 |
|---|---|
| `MF_MT_AVG_BITRATE` 放**输出**媒体类型 | ✅ 生效，误差 <5% |
| `MF_MT_AVG_BITRATE` 放**输入**媒体类型 | ⚠️ 被忽略（产物大小与不设时完全一致） |
| 完全不设 | ⚠️ 小分辨率时编码器**完全不出帧**（64x64 不设 → `Finalize` 报 `0xC00D4A44`）；320x240 不设时 MF 自算的默认码率恰好合法，**能跑通是巧合** |

⇒ **码率是必选项**，不能当成"可调优化"。

### 4.3 颜色属性：`MF_MT_VIDEO_NOMINAL_RANGE` 是最大的坑

| 设置（放**输入**媒体类型） | 结果 |
|---|---|
| `MF_MT_VIDEO_NOMINAL_RANGE = 0`（Unknown） | ❌ `Finalize` → `0xC00D4A44` |
| `MF_MT_VIDEO_NOMINAL_RANGE = 1`（Limited 16-235） | ❌ `Finalize` → `0xC00D4A44` |
| **`MF_MT_VIDEO_NOMINAL_RANGE = 2`（Full 0-255）** | ✅ 通过 |
| 只设 `MF_MT_YUV_MATRIX`（BT.709） | ✅ 通过 |
| 只设 `MF_MT_TRANSFER_FUNCTION`（709） | ✅ 通过 |
| 只设 `MF_MT_VIDEO_PRIMARIES`（BT.709） | ✅ 通过 |

颜色属性放**输出**媒体类型上会报 `SetInputMediaType 失败 0xC00D36B4「Invalid average bitrate」`（早期误判为码率问题，实为该属性的副作用）。

**⇒ 我们自己产出 full range（0-255）的 NV12，编码器负责转成 limited range 写进码流。** ffprobe 确认输出 `color_range=tv`，符合标准。

### 4.4 末尾固定丢 ~3 帧

| 输入帧数 | 输出帧数 | 时间戳 |
|---|---|---|
| 30 | 26 ~ 27 | 连续，从 0 开始 |
| 300 | **297** | `0.000000` … `9.866667` 连续 |

丢的是**尾巴**（时间戳连续 → 不是头部被吞，也不是中间跳段），是编码器流水线的尾帧没被 `Flush` 冲出来。

⇒ **收尾时补写几帧填充**（静止的重复帧即可，无视觉影响）。

### 4.5 `MF_MT_ALL_SAMPLES_INDEPENDENT` 无害

放输入 / 放输出 / 完全不放，三种结果**完全一致**（297 帧、4,784,378 字节，逐字节相同）。且 `key_frame=1` 只出现在首帧 ⇒ **不会**导致每帧都成关键帧，文件不会异常膨胀。

### 4.6 SinkWriter 基本用法

```rust
// 1) 要完整文件路径，不是 file:// URL（后者报 0x8007007B）
let sink_writer: IMFSinkWriter =
    MFCreateSinkWriterFromURL(PCWSTR(path.as_ptr()), None, &attrs)?;

// 2) 显式声明 MP4 容器（MFTranscodeContainerType_MPEG4，不是 MFVideoFormat_MP4）
attrs.SetGUID(&MF_TRANSCODE_CONTAINERTYPE, &MFTranscodeContainerType_MPEG4)?;

// 3) AddStream 给**目标**媒体类型，让 SinkWriter 自己挑编码器
let stream_index = sink_writer.AddStream(&out_type)?;
sink_writer.SetInputMediaType(stream_index, &in_type, None)?;

// 4) 写帧：必须 MFCreateMemoryBuffer + AddBuffer + SetCurrentLength
let buffer = MFCreateMemoryBuffer(frame_bytes as u32)?;
buffer.Lock(&mut ptr, Some(&mut len), None)?;
std::ptr::copy_nonoverlapping(src.as_ptr(), ptr, frame_bytes);
buffer.Unlock()?;
buffer.SetCurrentLength(frame_bytes as u32)?;   // ← 不设则 sample 长度为 0
sample.AddBuffer(&buffer)?;
sample.SetSampleTime(pts_100ns)?;
sample.SetSampleDuration(dur_100ns)?;
sink_writer.WriteSample(stream_index, &sample)?;

// 5) 收尾
sink_writer.Flush(stream_index)?;
sink_writer.Finalize()?;
```

其它要点：

- `MFCreateSample()` 后取 `ConvertToContiguousBuffer()` 会失败（`0x8000FFFF`），必须用 memory buffer。
- `MF_SINK_WRITER_DISABLE_THROTTLING = 1` 实测**不导致**帧丢失（节流开/关都是丢 3 帧），但录屏是实时投递，**保持默认节流**更稳。
- `MF_READWRITE_ENABLE_HARDWARE_TRANSFORMS = 1` 开启硬件变换路径。

### 4.7 windows-rs 0.61 的 API 缺口

| 想要 | 实际情况 |
|---|---|
| `MFVideoFormat_B8G8R8A8UIntNormalized` | **不存在**，只有 `MFVideoFormat_RGB32` |
| `MFVideoColorSpace` 枚举 | **未导出**（`MFVideoPrimaries` / `MFVideoTransferFunction` 都有，唯独缺它）→ 按 mfapi.h 取值手补常量（BT709 = 1） |
| `IMFSinkWriter` 的继承关系 | windows-rs **把继承展平**了：`interface_hierarchy!(IMFSinkWriter, IUnknown)`，**没有** `AddStreamSink` / `SetOutputMediaType`；QI `IMFMediaSink` 失败（`0x80004002`）→ 用 `AddStream(目标类型)` |
| feature 名 | `Win32_Media_MediaFoundation`（不是 `Media_Foundation`） |
| 媒体类型常量位置 | `MFVideoFormat_*` / `MF_MT_*` 全在 `Windows::Win32::Media::MediaFoundation` 模块内，**无独立 MediaProperties 模块** |

## 5. 架构设计

### 5.1 模块落点（不动现有四 crate 链）

依赖方向维持 `core ← capture ← ui ← app` 单向，**不新增 crate**：

| 模块 | 位置 | 职责 | 依赖 |
|---|---|---|---|
| `src/nv12.rs` | **screenloom-core** | 纯 Rust BGRA→NV12 转换（full range / BT.709） | 无（core 不依赖 windows crate） |
| `src/stream.rs` | **screenloom-capture** | 持续帧源：WGC 帧池常驻、只保留最新帧、墙钟打时间戳 | core + windows |
| `src/record/mod.rs` | **screenloom-app** | 录制会话编排（起停 worker 线程、状态回投 UI 线程） | core + capture + windows |
| `src/record/encoder.rs` | **screenloom-app** | MF SinkWriter 封装 | windows |
| `src/recorder_hud.rs` | **screenloom-ui** | REC 指示器浮窗（红点 + 计时 + 停止按钮） | core + windows |
| `config.rs` | **screenloom-core** | 新增 `record_hotkey` / `record_fps` / `record_bitrate` / `record_dir` | 无 |

**为什么编码器放 app 而不是新建 crate**

1. app 里已有 `ocr.rs` / `ai.rs` / `clipboard.rs` 这批平台集成模块，`longshot.rs` 整个长截图特性也在 app —— 录屏同属"编排 + 平台集成"。
2. 现有 AI/OCR 的分层模式是「**ui 提供控件 + app 装回调**」（`overlay.set_ai_handler(...)` + `screenloom_ui::post_ai_reply`），录屏 HUD 正好复用同一套模式，不需要 ui 反向依赖编码器。
3. 零新增依赖、零新增 crate，符合项目既有约束。

### 5.2 线程模型

```
UI 线程（主）                      worker 线程
─────────────                     ────────────
热键 / 托盘 / HUD                 WGC 帧源
      │                                │
      │  PostMessageW ◄──── 状态 ───────┤
      │                                ▼
      │                          BGRA→NV12
      │                                │
      │                                ▼
      │                          MF SinkWriter → MP4
      ▼
停止：AtomicBool = true  ─────────────►
      join()
```

要点：

- worker 线程**自己** `CoInitializeEx(COINIT_MULTITHREADED)`，并在**该线程内**创建 `WgcBackend`。
- `WgcBackend` 内部的 `_apartment: ComApartment` 守卫保证**套间活得比 WinRT 对象久** —— 这是 `wgc.rs` 里写死的硬规则，录屏同样适用（`WgcBackend` 必须在 worker 线程内创建、并在 worker 线程退出前析构）。
- UI 线程**不碰** COM/WinRT 录制对象，只通过 `PostMessageW` 收状态。

### 5.3 帧率与时间戳（最容易做错的地方）

WGC 的出帧速率由画面变化决定 —— 静态桌面可能几秒才产生一帧。

**只用一种时间戳都会出问题，两个极端都有前车之鉴：**

| 做法 | 后果 | 出处 |
|---|---|---|
| `pts = 帧号 × (1/30)`，**不重同步** | 静止画面录出来会**快进**（画面不变但时间在飞）；15 秒的缓冲能产出 26 秒的视频 | carnmorcyber 录屏器 v1.1.1 实测踩坑 |
| `pts = 真实墙钟` | 采集抖动（4~20 ms 的帧间隙）被原样带进码流 → **播放卡顿**，抖动从 0 ms 涨到 15.68 ms | carnmorcyber v1.3.2 实测踩坑 |

**正确做法：合成时间戳 + 落后重同步（OBS 的做法）**

1. 帧源记录每帧的**捕获墙钟时刻**（`Instant`）；
2. 编码时按**目标帧率**节流：距上一帧写入不足 `1/fps` 就**丢掉这一帧**（丢旧留新）；
3. `SetSampleTime` 写 **合成时间戳**：`pts_n = n × (1/fps)`，保证输出是严格 CFR、帧间距均匀；
4. **burst guard**：若当前墙钟已落后合成时间轴超过 2 个帧间隔（说明中间丢了很多帧），就把合成时间轴**重置到当前墙钟**，避免静止画面被"压缩"成快进。

> 合成时间戳解决"抖动"，重同步解决"快进"，两者缺一不可。

**另外两条来自 OBS / 其它实现的经验：**

- 采集线程要**跑满**（尽可能快地取帧），由**时间戳**决定哪一帧该进编码器，而不是让采集线程自己去 sleep 节流。
- 帧队列积压时**丢弃旧帧**（保留最新），否则录出来会一直是慢动作。

### 5.4 分辨率与颜色

- 输入 NV12 要求**宽高为偶数**（色度 2×2 降采样）。奇数尺寸的显示器需**向上取整补边**。
- 尺寸在录制期间**不可变**（H.264 码流不允许中途改分辨率）。
- 色彩转换走 **BT.709 / full range**，与 §4.3 的实测结论一致。

### 5.5 落盘

| | |
|---|---|
| 目录 | `%USERPROFILE%\Videos\Screenloom\`（取不到则退回 `Pictures\Screenloom`） |
| 文件名 | `Screenloom_YYYYMMDD_HHMMSS.mp4` |
| 收尾 | `Flush` → 补写几帧填充 → `Finalize`（**moov 必须 Finalize 才写**，中途被杀 → 文件不可播） |

### 5.6 音频：建议首版不做

WASAPI 回环采集（`AUDCLNT_STREAMFLAGS_LOOPBACK`）+ SinkWriter 第二条流 + AAC 编码器，是与视频**正交**的一大块工作量。

纯视频 MP4 本身就是一个成立的 user-visible 特性，音频作为 M3 单独做。

## 6. 风险清单

| # | 风险 | 后果 | 对策 | 怎么验 |
|---|---|---|---|---|
| 1 | **混合显卡**（RTX 500 Ada + Intel 核显），硬件编码器可能落到核显甚至软编 | 1080p 实时性未知，可能掉帧 | 优先用 MFT 枚举出的 HARDWARE 编码器；不可用时退回软件编码器（性能另议） | **必须先测**：录 60 秒，`ffprobe -count_frames` 核对 `nb_frames ≈ duration × fps` |
| 2 | BGRA→NV12 全屏 1080p@30 ≈ **93 MB/s 输入** + ~186 MB/s 写 | CPU 吃 1~2 核 | 先纯 Rust 实现并 benchmark；必要时上 GPU 路径（M4） | 录 60 秒看 CPU 占用 |
| 3 | 虚拟屏尺寸中途变化（改分辨率 / 拔显示器） | 编码器分辨率不能改 | **首版只支持单显示器录制**；或检测到变化就结束当前文件另开新文件（分段录制） | 录制中改分辨率 |
| 4 | 进程被强杀 / 崩溃 | MP4 缺 `moov` 不可播 | 正常退出路径保证 `Flush`+`Finalize`；异常退出的文件提示"可能损坏" | 任务管理器强杀后 `ffprobe` |
| 5 | 末尾固定丢 ~3 帧 | 尾部 ~100 ms 内容缺失 | 收尾补写填充帧 | `ffprobe -count_frames` 核对帧数 |
| 6 | WGC 对 DRM 保护内容输出黑帧 | 部分窗口录出来是黑的 | 正常现象，写进文档 | 播放受保护视频时录制 |
| 7 | 录屏热键被其它软件占用 | 注册静默失效 | 注册失败必须提示，不能吞 | 故意用冲突热键启动 |
| 8 | 长时间录制文件巨大 | 占满磁盘 | 录制前预估空间 / 录制中显示已用体积 | 录 1 小时看体积 |
| 9 | **硬件光标缺失**（走 DXGI Dup 时会隐藏硬件光标；走 WGC 时则由系统合成，需实测确认） | 录出来看不到鼠标 | 若走 DXGI：需 `GetFramePointerShape` 取形状并叠加；WGC 侧需实测 | 录一段有鼠标移动的画面后逐帧看 |
| 10 | `DXGI_ERROR_ACCESS_LOST`（驱动更新 / 改分辨率 / 锁屏 / 切远程桌面） | 采集直接崩 | 首版走 WGC（不受此影响）；若将来上 DXGI 必须实现重建逻辑 | 录制中锁屏 / 改分辨率 |

## 7. 分阶段里程碑

> 严格区分 **infrastructure（基础设施）** 与 **user-visible（用户能用）**。
> M0 全做完**不等于**"有录屏功能"，对外沟通时不能混。

### M0 · 基础设施（**不是功能完成**）

| 交付物 | 验收判据 |
|---|---|
| `core/src/nv12.rs` | 单测：已知色块 → 期望 YUV 值（BT.709 full range，含 R/G/B/灰/黑/白） |
| `app/src/record/encoder.rs` | 单测：合成 NV12 → 编码 → 断言产物含 `ftyp`/`moov`/`mdat` 且 `ffprobe` 可读 |
| `capture/src/stream.rs` | 连续取帧：3 秒内产出 ≥N 帧，且每帧带墙钟时间戳 |
| 码率 / 颜色 / 补帧 | 单测覆盖 §4.2 §4.3 §4.4 三条结论 |
| 时间戳 | 单测覆盖 §5.3：合成时间戳步进正确 + burst guard 在落后 > 2 帧间隔时重同步 |

### M1 · **用户能用**（到这里才算「有录屏功能」）

- `screenloom --record 10 --record-out PATH` → 10 秒后产出可播放 MP4
- 托盘菜单「开始录屏 / 停止录屏」
- 第二个全局热键（默认 `Alt+R`）
- REC HUD（红点 + 计时 + 停止按钮）
- 自动落盘到 `Videos\Screenloom` + 结束提示

### M2 · 体验

- 录制范围可选（单显示器 / 整块虚拟屏）
- 帧率 / 码率可配
- 录完自动打开所在文件夹

### M3 · 音频

- WASAPI 回环采集 + AAC，与视频合成 MP4

### M4 · 性能

- DXGI Desktop Duplication 零拷贝
- GPU 侧色彩转换
- 多显示器分段录制

## 9. 可借鉴的开源项目

> 微信 PC 4.x 本身没有录屏（§2），所以**没有上游可抄**；下面这些是外部参照物。
> 按「和我们的重合度」排序，不是按知名度排序。

### 9.1 技术栈最接近的（Rust + Windows + 硬件编码）

| 项目 | 技术栈 | 能借鉴什么 |
|---|---|---|
| [neerajsunil/pip-recorder](https://github.com/neerajsunil/pip-recorder) | Rust，Windows 11，WGC 抓屏，NVENC / QuickSync 硬件编码，H.264/HEVC/AV1 → MP4，桌面音频 + 麦克风，Slint UI | **最直接的对照物**：同为 Rust + Windows + 硬件 H.264 + MP4。看它怎么切 crate、怎么选编码器、UI 怎么做 |
| `rs-capture-pipeline` / `capture-runtime`（Rust crate） | WGC → **GPU 路径 BGRA→NV12** → NVENC（不可用时 OpenH264 兜底）→ MP4/H.264；WASAPI loopback + AAC/Opus；用 channel 把 `VideoPacket`/`AudioChunk` 交给宿主 | **架构与我们的 core/capture/app 分层几乎一一对应**。它的实测报告坦承：写出的 1080p 文件只有 ~53fps 而非 60fps，属 "muxing / pacing / capture cadence" 问题 —— 正是我们 §5.3 要处理的 |
| [CapSoftware/Cap](https://github.com/CapSoftware/Cap) | Rust + Tauri，`crates/scap-*` 采集抽象、`crates/rendering`(WGPU)、`crates/enc-ffmpeg`、多轨音频 | **trait 化的采集/编码/输出分层**可借鉴；**编码层不可借鉴**（走 FFmpeg） |
| [screenpipe](https://github.com/mediar-ai/screenpipe) | Rust，`WindowsGraphicsCapture` 源，Source → Filter → Encoder → Sink 管道 | 管道式抽象（缩放/帧率/打码都做成 Filter），和我们 core 层纯算法的定位一致 |

### 9.2 Windows 上的成熟实现（功能与 UX 标杆）

| 项目 | 能借鉴什么 |
|---|---|
| **OBS Studio**（GPLv2） | 事实上的工业标准：**合成时间戳 + CFR 输出**、帧节奏、编码器抽象（x264/NVENC/QSV/AMF）、MP4 muxing、热键与状态机 |
| [ScreenToGif](https://github.com/NickeManarin/ScreenToGif)（MIT，C#/WPF） | 采集方式可在 **BitBlt / DirectX Desktop Duplication / Graphics Capture API / WGC** 之间切换（设置界面）；`ICapture → BaseCapture → DirectImageCapture → DirectCachedCapture` 的采集抽象层次；**光标合成**（单色 / 带透明 / 掩码三种绘制）；"移除重复帧"；导出可选 **FFmpeg** 或**系统编码器**（← 正好对照我们走 MF） |
| **ShareX**（GPLv3，C#） | Windows 录屏的**功能集标杆**：区域/窗口/全屏、热键体系、托盘、录完动作（打开文件夹/复制/上传）、录制后处理 |
| **Captura**（MIT，C#/WPF，已停更） | 早期就有 WGC + **Media Foundation** 源，和我们的技术路线重合，可看它怎么组织 MF 调用 |
| [wl-screenrec](https://github.com/russelltg/wl-screenrec)（Rust，Wayland） | **零拷贝 GPU 路径**的标杆。实测对比：wf-recorder CPU ~500%，wl-screenrec ~2.5% —— 这是我们 M4 走 GPU 路径的收益量化依据 |

### 9.3 已经踩过、我们可以直接避开的坑

来自 `carnmorcyber` 的纯 C 录屏器开发记录（v0.9 → v1.3.5，每版重写）：

| 版本 | 做法 | 结果 |
|---|---|---|
| v1.0.0 | **MF 软编 H.264 + CPU 上 BGRA→NV12** | **1080p 以上必然掉帧** —— 直接印证我们 §6 风险 2 |
| v1.1.0 | 换 NVENC + GPU 色彩转换 | 性能问题解决，但两个 D3D11 设备跨设备同步会**死锁** |
| v1.1.1 | 时间戳按**帧数**算 | 15 秒缓冲产出 **26 秒**视频 |
| v1.2.0 | 布尔标志 + 忙轮询 | 换成**状态机 + Windows 事件对象**（`WaitForMultipleObjects`），删掉 700 行死代码 |
| v1.3.0 | NVENC 改用 CUDA 统一设备 | 无跨设备死锁，120fps 连续 53 分钟零停顿 |
| v1.3.2 | 时间戳改**合成时间戳** | 抖动从 15.68 ms 降到 **0 ms** —— 促成我们 §5.3 的修正 |

其它可直接抄的经验：

| 主题 | 结论 |
|---|---|
| 采集线程 | 要**跑满**取帧，由时间戳决定哪帧进编码器；别让采集线程自己 sleep |
| 丢帧 | 队列积压 > 5 帧就**丢弃旧帧**（保留最新），否则录出来是慢动作 |
| 收尾 | 先停采集 → **flush 编码器** → 再关文件，否则最后几秒丢失（对应我们的补帧） |
| 码率 | 1080p 录屏 **8~12 Mbps**；纯代码/PPT 6 Mbps；游戏 16+ Mbps |
| 音频 | WASAPI loopback 的格式**必须 `GetMixFormat` 查**，写死必错 |
| 音视频同步 | 统一用 **QPC** 高精度时间源，别各用各的 |
| 硬件编码 | 4K 下 x264 CPU 60%+ vs NVENC ~10%，画质肉眼几乎无差 |
| 光标 | DXGI Dup 会**隐藏硬件光标**，要 `GetFramePointerShape` 手动叠加 |
| `DXGI_ERROR_ACCESS_LOST` | 驱动更新 / 改分辨率 / 锁屏 / 切远程桌面都会触发，必须能重建 |
| `moov` | 实时录制 moov 在**文件尾**，中断即损坏；ffmpeg 的 `movflags=faststart` 可前移（MF 侧无等价开关） |

### 9.4 底层工具链

| | 可借鉴什么 |
|---|---|
| **FFmpeg** 的 `gdigrab` / `dshow` / `d3d11va` | Windows 采集侧的参考实现；`movflags=faststart` 对应我们的 moov 风险 |
| **GStreamer** 的 `d3d11capture` / `dxgiscapture` 元素 | 管线式架构；`appsink`/`h264parse`/`mp4mux` 的衔接方式 |

## 10. 附：本文涉及的实测命令

```powershell
# 编码器枚举
#   MFTEnumEx(MFT_CATEGORY_VIDEO_ENCODER, SYNCMFT | HARDWARE, ...)

# 帧数核对（注意用 -count_frames，实际解码而非读元数据）
ffprobe -v error -select_streams v:0 -count_frames `
  -show_entries stream=nb_read_frames,avg_frame_rate,color_range `
  -show_entries format=duration,size,bit_rate -of default=noprint_wrappers=1 out.mp4

# 首尾时间戳（判断丢的是头还是尾）
ffprobe -v error -select_streams v:0 -show_entries frame=pts_time,key_frame -of csv=p=0 out.mp4
```
