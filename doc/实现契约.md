**必须支持的降级路径**：WGC 不可用（Win10 < 1903）、目标是被保护窗口、创建帧池失败 → 自动切 GDI `BitBlt`；窗口模式失败 → `PrintWindow`。

### 4.1 虚拟屏整屏抓取契约（**关键**）

浮窗（`screenloom-ui::Overlay`）是铺在 **整块虚拟屏** 上的，它期望的背景帧必须满足：

```text
图像内坐标 = 虚拟屏物理坐标 − virtual_origin
图像尺寸   = virtual_screen_size()
frame.bounds = Rect::new(origin.x, origin.y, size.w, size.h)
```

只抓「主显示器」是**错的**：浮窗会把主屏画面贴到虚拟屏左上角，内容和位置都错，跨屏选区还会被算到错误的屏幕空间。

`capture_virtual_screen` 的两条路径：

1. **逐显示器抓再合成**（优先）：走 WGC，逐块 `Monitor(i)` 抓，贴到虚拟屏画布的 `bounds - origin` 偏移处。
   任一块的图像尺寸与该显示器物理边界不一致（会错位）→ 直接走路径 2。
2. **GDI 整块一次 `BitBlt`**（兜底）：屏幕 DC 坐标与虚拟屏坐标 **1:1**（`SM_XVIRTUALSCREEN` 给的是左/上边界，
   **不是 DC 原点**），所以源点直接用虚拟屏坐标（可能为负）就能一次抓到跨屏画面，且是原子的、无跨屏接缝。

显示器之间的 **空隙**（虚拟屏上不属于任何显示器的区域）合成后是透明/黑的 —— 这是正确的，
浮窗在这些位置自然透出真实桌面。

## 5. `screenloom-ui` 契约

```rust
pub struct OverlayConfig {
    pub virtual_origin: Point,
    pub scale: f32,
    pub hide_from_capture: bool,
}

/// 分层浮窗（全屏 + 每像素 alpha），承载选区与编辑器
pub struct Overlay { /* hwnd, canvas, state */ }
impl Overlay {
    pub fn new(cfg: OverlayConfig) -> Result<Overlay, Error>;
    /// 背景 = 抓到的 **整块虚拟屏**（见 §4.1）。失败必须返回 Err，不能吞掉。
    pub fn show(&mut self, bg: &RgbaImage) -> Result<(), Error>;
    pub fn run(&mut self) -> Result<OverlayOutcome, Error>;  // 事件循环
    /// 程序化设置选区（逻辑坐标）
    pub fn set_selection(&mut self, r: Rect);
    /// 程序化设置选区（图像内物理像素，与 `Selected::region` 同坐标系）—— 脚本化/自动化用
    pub fn set_selection_physical(&mut self, r: Rect);
    /// 程序化确认选区（等价于点工具栏「完成」）
    pub fn confirm(&mut self);
}

pub enum OverlayOutcome {
    Cancelled,
    Selected { region: Rect, canvas: Canvas, action: OverlayAction },
}

pub enum OverlayAction { Confirm, Copy, Save, Pin }

/// 贴图浮窗（置顶常驻）
pub struct PinWindow { /* ... */ }
impl PinWindow {
    pub fn new(image: RgbaImage) -> Result<PinWindow, Error>;
    pub fn show(self);
}
```

**坐标系三层（不得混用）**：

| 层 | 含义 | 换算入口 |
|---|---|---|
| 虚拟屏物理 | 原点 = 主显示器左上角，副屏可负 | `virtual_screen_origin()` / `virtual_screen_size()` |
| 图像内物理 | 原点 = 背景帧左上角 = 虚拟屏左上角 | `虚拟屏物理 − virtual_origin` |
| 逻辑 | 浮窗 UI 用的坐标 | `Rect::to_physical` / `Rect::to_logical`（**只走这两个**） |

`OverlayOutcome::Selected::region` 是 **图像内物理像素**，可直接 `frame.image.crop(region)`。

**渲染统一走 GDI+**：`GdipCreateBitmapFromScan0`（32bpp PARGB）→ `GdipGetImageGraphicsContext` → 绘制 → `GdipBitmapLockBits` 取像素 → `UpdateLayeredWindow(ULW_ALPHA)`。

## 6. 事件流（主编排）

```
RegisterHotKey(Alt+A)
      │
      ▼
[1] 采集背景 ──► capture::capture_virtual_screen(backend)   ← 整块虚拟屏，不是单块显示器
      │            期间用 SetWindowDisplayAffinity 隐藏自身
      ▼
[2] 选区浮窗 ──► ui::Overlay::show(bg) ──► 拖拽/缩放/锁定/Esc
      │            └─ 命中窗口过滤时可选目标窗口（对齐 window_filter_t）
      ▼
[3] 截取区域 ──► image.crop(region)          region 是图像内物理像素
      ▼
[4] 编辑器 ────► ui::Overlay::show(region_img) + 工具栏
      │            图形/文字/马赛克/取色/裁剪/撤销
      ▼
[5] 动作分发 ──► copy | save | pin | long_screenshot | ocr
      │            工具栏 AI 三件套：ask_ai | translate | ai_mosaic  → 后台线程调模型，见 §7.9
```

长截图（滚动截图）子流程：

```
capture 第 1 帧 ──► 用户滚动/按方向键 ──► capture 第 N 帧
        │                                        │
        └────► stitch::match_offset ────────────┘
                     │ 命中 → splice 拼接
                     └─ 未命中 → 提示"截图中断，返回中断位置继续滚动"
```

> 长截图的每一帧也必须抓 **整块虚拟屏** 再按虚拟屏坐标裁剪 —— 选区可能跨显示器，
> 只抓单块显示器会把区域算错。

## 7. AI 接入契约（DeepSeek / MiniMax）

> 2026-11-04 用户指令：**「AI 可以使用 deepseek、minimax 接入」** ——
> 推翻原规格书 §11.4 坑位 #4「AI 一键打码的模型与服务端协议 —— 抓包（该部分应直接放弃复刻）」。
> 改为**真实接入公开大模型 API**（两家都是 OpenAI 兼容接口）。

### 7.1 能力边界

| 能力 | 微信原实现 | 本项目做法 |
|---|---|---|
| 问 AI | `wx::ScreenShoter::ask_ai` / `ask_ai_with_prompt`（腾讯内部服务，协议私有） | 调 **DeepSeek / MiniMax** 公开接口（多模态：图片 + 问题） |
| 翻译 | `WxShotEditormenu::translate_enter/leave`（腾讯内部翻译） | 本地 OCR 取字 → **LLM 翻译** |
| AI 一键打码 | `wx::AiMosaicButton`（腾讯内部模型，协议私有） | **LLM 输出归一化 bbox** → 像素层打码 |

**仍然不做**：微信内转发、表情插入（腾讯私有协议 / 进程内状态），保持返回「不可用」。

### 7.2 Provider 抽象（`screenloom-app/src/ai.rs`）

两家都提供 **OpenAI 兼容**的 `POST {base}/chat/completions`，请求体/响应体形状一致
→ **一套客户端**，按 Provider 切 endpoint + model。

| Provider | endpoint | 默认模型 | key 环境变量 | 支持看图 |
|---|---|---|---|---|
| `minimax` | `https://api.minimax.cn/v1/chat/completions` | `MiniMax-M3` | `MINIMAX_API_KEY` | ✅ |
| `deepseek` | `https://api.deepseek.com/chat/completions` | `deepseek-flash` | `DEEPSEEK_API_KEY` | ✅ |

> DeepSeek 的视觉模型现名 **`deepseek-flash`**（旧名 `deepseek-v4-flash-vision-exp` 是退役别名，仍被接受）。
> **非视觉模型传图直接 400**（`This model does not support image`）→ 默认模型必须是视觉模型。

### 7.3 请求体（OpenAI 兼容）

```json
{
  "model": "MiniMax-M3",
  "messages": [
    { "role": "user", "content": [
        { "type": "image_url", "image_url": { "url": "data:image/png;base64,...", "detail": "high" } },
        { "type": "text", "text": "这张图里是什么" }
    ]}
  ],
  "stream": false,
  "thinking": { "type": "adaptive" }
}
```

- 图片用 **data URL 内联**（`data:image/png;base64,...`），不传外链。
- 只用 **user 消息**带图（DeepSeek 视觉要求）。
- `detail`：DeepSeek 支持 `low|high|original|auto`，MiniMax 支持 `low|default|high` → 取交集 **`high`**。
- 图片限制：DeepSeek 单图 ≤32MiB / 边长 ≤8192px；MiniMax 单图 ≤10MB。两边都收 JPEG/PNG/GIF/WebP。
- `thinking` 是 **MiniMax 专属**字段，只在 provider=MiniMax 且模型名含 `minimax` 时才加（DeepSeek 侧不加）。

### 7.4 响应与错误

- 成功：`choices[0].message.content`（字符串）；少数模型给数组 → 取 `type=="text"` 的拼接。
- MiniMax 另有 `reasoning_content`（思考内容），本项目**不用**。
- 错误体两套形状，都由 `describe_error(status, body)` 统一翻译成人话：

| 来源 | 形状 | 常见码 |
|---|---|---|
| OpenAI / DeepSeek | `{"error":{"message":...,"type":...}}` | 401 key 无效 |
| MiniMax | `{"base_resp":{"status_code":1004,"status_msg":...}}` | 1004 鉴权失败 / 1008 余额不足 / 1002 限流 / 2013 参数错误 |

状态码提示：401/403 → key 不对；402 → 余额不足；429 → 限流；400 → 参数/模型不支持图片。

### 7.5 AI 一键打码：归一化 bbox

模型输出 **归一化 0..1 的 bbox**（避免模型直接给像素坐标时的分辨率歧义）：

```json
{"regions":[{"x":0.12,"y":0.34,"w":0.18,"h":0.22,"label":"人脸"}]}
```

解析器 `parse_regions` 容忍：```json 代码块包裹 / 顶层是数组 / 键名 `x,y,w,h` 或
`left,top,width,height` 或 `bbox:[x,y,w,h]` / **归一化 vs 像素**（四个值都 ≤1 视为归一化）。
坐标映射 `MosaicRegion::to_rect(img_w, img_h)` 负责换算并裁剪进图像范围。

### 7.6 传输层：WinHTTP（不引第三方 TLS 栈）

`screenloom-app/src/http.rs` 用 Windows 自带 **WinHTTP**：

- 理由：TLS 后端要么 `aws-lc-rs`/`ring`（要 C 编译器，本机 `cl.exe` 不在 PATH），
  要么 `native-tls`（还得挑证书后端、绑死 Schannel/OpenSSL）；WinHTTP 用**系统证书库**。
- AI 接入总共只加 **两个纯 Rust 依赖**：`serde_json`（请求体构造 / 响应解析）+ `base64`（图片内联）。
- 端点、模型、key 都可被覆盖（命令行 / 环境变量 / 配置文件）。

### 7.7 配置（环境变量 + 配置文件）

| 来源 | 键 | 说明 |
|---|---|---|
| 环境变量 | `MINIMAX_API_KEY` / `DEEPSEEK_API_KEY` | **优先** |
| 配置文件 | `ai_key_minimax` / `ai_key_deepseek` | provider 专用 |
| 配置文件 | `ai_api_key` | 通用兜底 |
| 配置文件 | `ai_provider` | `minimax`(默认) / `deepseek` |
| 配置文件 | `ai_model` | 空 = 用 provider 默认模型 |
| 配置文件 | `ai_endpoint` | 空 = 用 provider 默认端点 |
| 配置文件 | `ai_timeout` | 秒，默认 120 |

**不硬编码任何 key。**

endpoint 解析顺序：命令行 `--endpoint` > 配置文件 `ai_endpoint`（**仅当配置里的 provider == 生效的 provider**）> provider 默认。
（否则命令行切了 provider 却仍拿旧 provider 的端点 → key 与端点不匹配 → 401。）

### 7.8 两个入口

**命令行**（`screenloom-app/src/aicli.rs`）：

| 参数 | 说明 |
|---|---|
| `--ask "问题"` | 问 AI（图片默认取**剪贴板**，与 `--ocr` 的做法一致） |
| `--translate [语言]` | 翻译图里的文字（本地 OCR → LLM，默认英文） |
| `--ai-mosaic` | AI 一键打码（打码后存盘 + 复制到剪贴板） |
| `--image PATH` | 指定输入图片（默认剪贴板） |
| `--provider NAME` / `--model NAME` / `--endpoint URL` | 覆盖服务方 / 模型 / 端点 |
| `--ai-out DIR` / `--ai-block N` | 打码输出目录 / 马赛克块边长 |
| `--ai-probe` | **连通性探针**：不需要 key，发最小请求，预期 **401**（证明 DNS+TLS+HTTP 通） |

**工具栏**（`screenloom-ui`）：编辑态工具栏的 AI 组是三个按钮 ——「问 AI」「翻译」「AI打码」。

**工具栏 · 本地组**（同一条工具栏，AI 组之后）：

| 按钮 | 动作 | 需要 key | 落地 |
|---|---|---|---|
| **提取文字** | 选区图像 → **本地** OCR（`Windows.Media.Ocr`）→ 结果面板 + 复制到剪贴板 | **否** | `Overlay::set_ocr_handler`（独立于 AI handler，**无条件装上**）；app 层 `install_ocr_handler` |
| **滚动截图** | 对当前选区跑滚动拼接（`Enter` 继续 / `Esc` 结束），结果自动存盘 + 复制 | 否 | 新增 `OverlayAction::LongShot` → app 层 `want_long = long \|\| action == LongShot` |

两者都复用 AI 的「后台线程 → `post_ai_reply` 回投 → 结果面板」机制，
所以**不会卡住 UI 线程**；结果面板标题分别是「提取文字」。

> 坑见附录 B.3 #40（OCR 路径的 `\\?\` 前缀）、#41（浮窗退出残留 `WM_QUIT`）、
> #42（`WS_POPUP` 提示窗不拿焦点）。这三条都让「长截图 / 提取文字」**表面有按钮、实际不可用**。

### 7.9 线程模型（关键）

AI 调用**阻塞且耗时**，绝不能占用 UI 线程：

```
[UI 线程]   点「问 AI」→ 弹 EDIT 收问题 → 裁出选区图像
               └─► 调用 handler(AiRequest{..})    ← handler 必须**立刻返回**
[后台线程]   handler 内 std::thread::spawn → 调 API
               └─► screenloom_ui::post_ai_reply(hwnd, reply)
[UI 线程]   收到 WM_AI_REPLY → 接管 Box → 画结果面板 / 生成马赛克标注
```

- 回投用自定义消息 `WM_AI_REPLY = WM_APP + 1`，`LPARAM` 传 `Box::into_raw(Box<AiReply>)`，
  浮窗侧 `Box::from_raw` 接管（谁投递谁释放）。
- `AiReply::MosaicRegions` 会被转成画布上的 `Annotation::Mosaic`（坐标相对裁剪图左上角），
  **立刻在像素层生效**（`base_pixels` 里的 `pixelate`）。
- 文本结果同时**复制到剪贴板**（面板放不下时全文在剪贴板）。
- `screenloom-ui` 不依赖 `screenloom-app`：`Overlay::set_ai_handler` 收一个
  `Fn(AiRequest) + Send + Sync + 'static` 闭包，具体怎么调模型由 app 层决定。

## 8. 设置页面 / 托盘 / 图标契约

### 8.1 分层原则（**禁止循环依赖**）

| 层 | 职责 | 禁止 |
|---|---|---|
| `screenloom-core/src/icon.rs` | **纯像素**画应用图标 + 打包 `.ico` | 不碰任何 Win32 API（保持 core 无平台依赖） |
| `screenloom-app/src/theme.rs` | **纯配色 + 绘制基元**（面板 / 标题 / 输入框 / 复选框 / 下拉框 / 按钮 / 菜单 / 焦点环） | 不含 Win32 窗口逻辑（只依赖 `screenloom_ui::gdiplus`） |
| `screenloom-app/src/settings/` | 设置窗口的**全部** Win32 控件逻辑 + 布局计算（拆为 `mod.rs` / `layout.rs` / `state.rs` / `paint.rs` / `controls.rs` / `combo.rs` / `validate.rs`） | 不依赖 `screenloom-ui`（只用它的 `gdiplus` 绘图后端） |
| `screenloom-app/src/tray.rs` | 托盘图标 + 右键菜单 | 不自己画图标（从 exe 的 PE 资源取） |
| `screenloom-ui/src/toolbar.rs` | 工具栏图形绘制 | 不弹设置窗口（只发请求） |

**关键约束**：`screenloom-ui` **不能**依赖 `screenloom-app`（否则循环依赖）。
所以浮窗工具栏上的「设置」按钮不能直接开窗，只能发请求：

```
Overlay::set_settings_handler(Box<dyn Fn() + Send + Sync>)
   → 点「设置」 → 回调 → app 层 settings::open(path)
```

托盘同理：`flow.rs` 注册托盘后拿到 `TrayCommand`，再决定调 `settings::open` 还是 `run_capture`。

### 8.5 关键：客户区高度 ≠ 整窗高度

`compute_layout(k)` 算的是**客户区**高度（`layout.client_h`），而 `CreateWindowExW` 的高是**整窗**高度（含标题栏 + 边框）。
少算这一层 → 底部「保存 / 取消」被标题栏挤到窗口外面（**看不见也点不到**）。

```rust
let (ww, wh) = frame_adjusted(px(WIN_W, k), state.layout.client_h, dpi);
```

`frame_adjusted` 内部用 `AdjustWindowRectExForDpi` 换算 —— DPI 感知，且标题栏样式变化时自动适配。
回归测试：`window_size_includes_title_bar_and_border`。

## 9. Windows API 坑位（务必按此实现）

| # | 坑 | 正确做法 |
|---|---|---|
| 1 | WGC 需要 COM apartment | 捕获线程必须 `CoInitializeEx(COINIT_MULTITHREADED)`；WinRT async 用 `windows::core::initialize_mta()` |
| 2 | D3D11 设备与帧池尺寸 | `Direct3D11CaptureFramePool` 尺寸变化会抛异常 → 捕获 `CreateFreeThreaded` 的 `SizeChanged` 事件重建帧池 |
| 3 | 帧是 GPU 纹理 | 必须 `CopyResource` 到 `D3D11_USAGE_STAGING` + `CPU_ACCESS_READ` 后 `Map` 才能读像素；不能直接访问 `ID3D11Texture2D` 的内存 |
| 4 | BGRA vs RGBA | WGC 帧是 **BGRA**；`RgbaImage::from_bgra` 负责换序。**这是最常见的 bug 源（截图整体发蓝/发红）** |
| 5 | 全局坐标 vs 逻辑坐标 | 浮窗用逻辑坐标，图像是物理像素；混合 DPI 下必须用 `GetDpiForWindow` 换算，`Rect::to_physical` 是唯一入口 |
| 6 | 分层窗 alpha | `UpdateLayeredWindow` 要求 **预乘 alpha** 的 BGRA；GDI+ `PixelFormat32bppPARGB` 正是预乘 |
| 7 | GDI+ 未初始化 | 进程启动时 `GdiplusStartup` 一次，退出时 `GdiplusShutdown`；否则 `GdipCreateFromHDC` 失败 |
| 8 | 中文文字 | 用系统字体族名（"Microsoft YaHei"/"SimSun"）走 `GdipCreateFontFamilyFromName`，**不要**自己找 TTF 文件（Windows 上中文字体多为 TTC） |
| 9 | 剪贴板格式 | 必须同时写 `CF_PNG`（PNG 字节）与 `CF_DIB`（BGRA + 负高度），否则 Chrome/Office 粘贴出黑图 |
| 10 | 全局热键 | `RegisterHotKey` 失败（被占用）要提示而不是静默；退出前 `UnregisterHotKey` |
| 11 | 抓自己 | 抓屏前 `SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE)`，抓完恢复 |
| 12 | 受保护窗口 | 命中"设备环境不允许当前应用截图"文案逻辑：捕获失败时给明确提示，而非空白图 |

| `SetClipboardData` | 第二参是 `Option<HANDLE>` | 传 `Some(HANDLE(..))` |
| `RegisterClipboardFormatW` | 接受 `Param<PCWSTR>`，用 `windows::core::w!("PNG")` | 不要用 `PCWSTR::from_raw(b"...")`（那是 u8 指针） |
| `Buffer` 无写入方法 | `windows::Storage::Streams::Buffer` 0.61 **只有** `Create`/`Length`/`Capacity`，**没有** `WriteBuffer` | 因此 `SoftwareBitmap::CreateCopyFromBuffer` 走不通；OCR 改走 **临时文件 → `StorageFile` → `BitmapDecoder` → `SoftwareBitmap`** |
| 异步 WinRT | `IAsyncOperation<T>::get()`（windows-future 0.2.1）可**阻塞**等待 | 每个 async 调一次 `.get()` 即可，不用 tokio |
| `BitmapDecoder` | `CreateAsync(&stream)` → `.get()`，再 `GetSoftwareBitmapAsync()` → `.get()` | |
| `GetSystemTime` vs `GetLocalTime` | 落盘时间戳**必须**用 `GetLocalTime` | 用 `GetSystemTime` 会存成 UTC，本地时间差 8 小时（实测 15:27 存成 07:27） |

### B.2 WGC（Windows.Graphics.Capture）在 windows-rs 0.61 的真实形状

> 这些是从 `windows-0.61.3/src/Windows/Graphics/Capture/mod.rs` 逐行查证的，**与常见博客写法不同**。

| 事项 | 0.61 的实际情况 | 正确写法 |
|---|---|---|
| `IGraphicsCaptureItem` 的方法 | vtable 只有 4 个：`DisplayName` / `Size` / `Closed` / `RemoveClosed`（mod.rs:494-500）。**没有 `CreateCaptureSession`，也没有 `ContentSize`** | item 的尺寸用窗口矩形；会话由帧池创建 |
| 创建会话 | 在**帧池**上，不在 item 上 | `pool.CreateCaptureSession(&item)?` |
| 取帧/表面 | `TryGetNextFrame` / `Surface` / `ContentSize` 都在**类**上（`impl Direct3D11CaptureFramePool` 65-146 行、`impl Direct3D11CaptureFrame` 6-48 行） | 直接调用，无需 cast |
| 帧池创建 | `CreateFreeThreaded(device, DirectXPixelFormat, numberofbuffers: i32, size: SizeInt32)` | `SizeInt32 { Width: i32, Height: i32 }`，路径 `windows::Graphics::SizeInt32` |
| 像素格式 | `DirectXPixelFormat::B8G8R8A8UIntNormalized`（=87） | 注意是 `UIntNormalized` 不是 `UNorm` |
| `BOOL` 类型 | 在 **windows-result 0.3** 的 `bool` 模块，经 `windows_core` 重导出 | `use windows::core::BOOL;`（**不在** `Win32::Foundation`） |
| `BitBlt` 返回值 | `windows_core::Result<()>` | 用 `.is_err()`，**不是** `.as_bool()` |
| `D3D11_CPU_ACCESS_READ` | `.0` 是 i32，结构体字段要 u32 | `D3D11_CPU_ACCESS_READ.0 as u32` |

### B.3 实测踩坑补充（2026-11-04 真机跑出来的）

| # | 坑 | 现象 | 正确做法 |
|---|---|---|---|
| 1 | **屏幕 DC 的坐标原点 ≠ 虚拟屏幕包围盒左上角** | GDI 抓屏得到**全零/全透明**图（看起来全白） | 屏幕 DC 的原点是**主显示器左上角 (0,0)**，与 `EnumDisplayMonitors` 给的虚拟坐标 **1:1**，左边/上边副屏用**负坐标**直接可达。`GetSystemMetrics(SM_XVIRTUALSCREEN)` 返回的是虚拟屏幕**左/上边界**（如 -1038/-1440），**不是** DC 原点——拿它做偏移就全落进桌面空洞。正确写法：`src = (x, y)`，不做任何偏移 |
| 2 | **屏幕 DC 不能 `DeleteDC`** | 句柄泄漏 / 无效操作 | `GetDC(None)` 拿到的 DC 必须 `ReleaseDC(None, dc)`；只有 `CreateCompatibleDC` 的才 `DeleteDC` |
| 3 | **WinRT 套间必须与对象同生命周期** | `0xC0000005` 访问违例 | `ComApartment` 守卫若只活在某个块里，`RoUninitialize()` 之后还在用该套间里创建的 WinRT 对象（如 `IDirect3DDevice`）→ 崩。守卫要**存进持有该对象的后端结构体** |
| 4 | **GDI+ flat API 的 PixelFormat 常量与 C++ 枚举不同** | `GdipCreateBitmapFromScan0` / `GdipBitmapLockBits` 一律返回 `Status=2 (InvalidParameter)` | `PixelFormat32bppPARGB` 的真实值是 **0x000E200B**（不是 C++ 头文件里的 0x00020006） |
| 5 | **GDI+ 的 `GpPath` 路径 API 画不出东西** | 圆角矩形填充/描边完全不可见 | `GdipCreatePath2` + `GdipAddPathArc` + `GdipFillPath` 这条路无效；改用「两个矩形 + 四个椭圆」拼出圆角矩形 |
| 6 | 32bpp DIB 的 **alpha 恒为 0** | 截出来的图在 PNG 里全透明 | GDI `BitBlt` 不写 alpha 通道；转 RGBA 时必须**自己填 255**，否则 PNG 全透明 |
| 7 | **只抓主显示器会让浮窗整体错位** | 浮窗盖住整块虚拟屏，但画面是主屏内容贴在虚拟屏左上角；跨屏选区算到错误屏幕 | 抓屏层必须提供 **整块虚拟屏** 的图像（`capture_virtual_screen`），见 §4.1 |
| 8 | **浮窗「看起来没画出来」不等于没画** | 选区模式下还没拖选时，浮窗内容与屏幕**像素级一致**（只压暗选区外），抓屏看不出区别 | 判定浮窗是否渲染要看 `GetWindowRect` / `IsWindowVisible`，或先拖出一个选区再看边框 |
| 9 | **`Overlay::show` 吞掉渲染错误** | 渲染失败时窗口照样显示但全透明，排查时毫无线索 | `show` 必须返回 `Result`，渲染/提交失败要往上抛 |
| 10 | **配置里空的 `default_dir` 不能当路径** | `default_dir =` 被解析成 `Some("")`，截图存到当前工作目录而不是 `Pictures\Screenloom` | 空值 → `None` |
| 11 | **WinHTTP 请求头长度不能算终止符** | `WinHttpSendRequest` 返回 `ERROR_INVALID_PARAMETER (0x80070057)` | `dwHeadersLength` 是**字符数**；缓冲区里补的两个 NUL 只是内存终止符，**不能计入长度**。`head_text = &head[..len-2]` |
| 12 | **标注坐标换算漏乘 `scale`** | 本机主屏 scale=1.25，浮窗上画的标注、存盘后的标注整体偏移 **25%** | 画布存的是**逻辑坐标**，输出坐标是**裁剪图物理像素**：`display_canvas` 必须先 `to_physical`（×scale）再减选区原点。见 §7 之外的 `Overlay::display_canvas` |
| 13 | **命令行切了 provider 却仍用旧端点** | 用 minimax 的 key 打 deepseek 的端点 → 401，误以为 key 错了 | 配置文件里的 `ai_endpoint` **仅当**配置 provider == 生效 provider 时才用；否则用 provider 默认端点 |
| 14 | **系统没有叫 `GROUPBOX` 的窗口类** | `CreateWindowExW` 用类名 `"GROUPBOX"` 返回错误 1406 且**静默失败**，分组边框与组标题全没了 | 分组框是 **BUTTON 类 + `BS_GROUPBOX` 样式**（`BS_GROUPBOX = 7`），不是独立窗口类 |
| 15 | **复选框与标签叠在同一位置** | 字段名被复选框盖住，看不出这一行是什么 | 复选框**自带文字**（Windows 标准做法），不要另建 STATIC 标签 |
| 16 | **`GetWindowRect` 是屏幕坐标，不能当客户区坐标用** | 「浏览…」按钮被放到窗口外面 | 在布局循环里直接记录布局坐标（`default_dir_geom`），不要事后反算 |
| 17 | **`SetWindowPos` 不带 `SWP_NOSIZE` 且 cy=0 会把控件压成 0 高** | 输入框整条消失 | 创建时就按正确宽高创建，别事后 resize |
| 18 | **先 `DestroyWindow` 再读控件** | 用户的改动全丢（`GetWindowTextW` 只能拿到空串） | 先 `collect()` 再销毁窗口；回归测试 `save_collects_before_destroying_window` 守护 |
| 19 | **客户区高度当整窗高度用** | 底部「保存 / 取消」被标题栏挤到窗口**外面**（看不见也点不到） | `CreateWindowExW` 的高是整窗高度，必须先过 `AdjustWindowRectExForDpi`（见 §8.5） |
| 20 | **`LoadImageW` 取本 exe 资源时 `hinst` 必须传 `Some(module_handle())`** | 传 `None` 会去系统资源里找 ID 1 → 找不到 → 托盘图标退化成默认图标 | `hinst` 传模块句柄。`MAKEINTRESOURCEW` 宏在 crate 里不存在 → 用 `PCWSTR(id as *const u16)` |
| 21 | **GROUPBOX 默认灰底把组标题盖住** | 分组标题颜色发灰、看不清 | 处理 `WM_CTLCOLORSTATIC` / `WM_CTLCOLORBTN`：`SetBkMode(TRANSPARENT)` + 返回 `GetSysColorBrush(COLOR_WINDOW)` |
| 22 | **`SendMessageW` 的第一个参数是 `HWND`，不是 `Option<HWND>`** | 编译不过 | `PostMessageW(hwnd: Option<HWND>, ...)` 才是 `Option`；`IsWindow(Option<HWND>) -> BOOL` 也直接返回不是 `Result` |
| 23 | **只编 `--examples` 不会重编 bin** | 改了 app 层代码，跑起来还是旧行为，误判「改了没用」 | 改 `screenloom-app` 后要 `cargo build --release -p screenloom-app --bins --examples` |
| 24 | **父窗口 WM_PAINT 不覆盖子控件区域** | 子控件画过一次的系统装饰（如原生按钮的**虚线焦点框**）会一直残留，父窗口重绘也擦不掉 | 要么让子控件自己不画焦点框，要么让子控件自己重绘。父窗口 `WM_PAINT` 里补画无效 |
| 25 | **原生 EDIT 漏了 `WS_TABSTOP`** | 初始焦点落到第一个 `WS_TABSTOP` 子控件（「浏览」按钮）→ 系统给它画虚线焦点框，看起来像 bug | 每个可聚焦的原生控件都要 `WS_TABSTOP`；自绘控件若不参与 Tab，则**不要**给 `WS_TABSTOP` |
| 26 | **owner-draw 原生按钮 + `WM_SETFOCUS` 重定向 → `BM_CLICK` 断链** | E2E 点「保存」后进程不退出、配置不写盘 | 放弃 owner-draw 路线，改用**完全自绘按钮类**（`ScreenloomFlatButton`）：自己实现绘制与鼠标，自己回发 `WM_COMMAND`，`BM_CLICK` 由自绘类响应 |
| 27 | **自绘下拉菜单画在父窗口内会被原生 EDIT 盖住** | 菜单弹出来被输入框挡住一半 | 下拉菜单用**独立 `WS_POPUP` 顶层窗口**，天然盖在所有子控件之上 |
| 28 | **`CreateCaret` 第二个参数是 `HBITMAP` 不是 `HBRUSH`** | 编译不过 / 插入符不显示 | `CreateCaret(hwnd, Some(HBITMAP(brush.0)), 1, h)` —— 把画刷句柄显式转成 `HBITMAP` |
| 29 | **`WM_NEXTDLGCTL` 只能用于对话框** | 用在普通窗口上，窗口被缩成 **199×34** 一条 | 普通窗口的 Tab 焦点自己管：子类化 + 宿主按 `FOCUS_ITEMS` 顺序 `SetFocus` |
| 30 | **圆角控件的四个角必须先填「背后色」** | 系统焦点框 / 下层内容从圆角缝隙里露出来 | 画圆角矩形**之前**先 `fill_rect` 整个控件矩形为背后色（面板色 / 窗口底色） |
| 31 | **PowerShell 5.1 的 `Get-Content`/`Set-Content` 往返改 UTF-8 源文件会双重编码中文** | 中文注释变成乱码；逆变换有损（245 字符不可还原），只能整文件重写 | 改源文件**只用** `edit` / `write` 工具；`Get-Content` 只用来**读**，且必须显式 `-Encoding UTF8` |
| 32 | **`SetWindowSubclass` 在 `UI::Shell`，不在 `UI::Controls`** | 找不到符号 / 编译不过 | `windows::Win32::UI::Shell::{SetWindowSubclass, DefSubclassProc, RemoveWindowSubclass}`；`SUBCLASSPROC` 是 `Option<fn>`，调用要写 `Some(proc)` |
| 33 | **留证截图没有判据 = 存下一张空图还当成功** | `settings_combo.png` 只有 **392 字节**，内容是**纯黑**，却一直被当成「下拉菜单已验证」 | 每次留证都要有**二值、可外部复核**的判据：① 抓图尺寸 == `GetWindowRect` 尺寸（证明 1:1 物理像素）；② 目标窗口/弹出窗口真的存在；③ 位图里存在**只有该界面才有的特征色像素数**（如菜单底色 `#232830`）。见 `scripts/capture_settings_theme.ps1` |
| 34 | **`SetForegroundWindow` 会吃前台锁** | 窗口明明在，抓屏却抓到**背后的 IDE**（`SetForegroundWindow` 返回成功也不代表生效） | 抓屏前用 `SetWindowPos(hwnd, HWND_TOPMOST, …, SWP_NOMOVE\|SWP_NOSIZE\|SWP_SHOWWINDOW)` **临时置顶**，抓完再取消 |
| 35 | **`std::sync::RwLock` 同一线程嵌套读锁会死锁** | 自绘主题改成运行时可读后，绘制函数里 `theme::current()` 又调了另一个也 `current()` 的函数 → 若此时有写者排队，线程互相等待，界面直接卡死 | 取值后**立刻**释放 guard（`let v = current().bg;`），不要把 guard 传进会再次取锁的函数；更不要在持有 guard 时调 `current()` |
| 36 | **DPI-unaware 进程里 `GetWindowRect` 返回的是虚拟化坐标** | 主屏 1.25 缩放时，818 物理像素的窗口被报成 **654**；`CopyFromScreen` 抓到的也是**缩小**的图 → 所有"尺寸相等"判据全部失真（自己跟自己比，永远相等） | 抓屏脚本**第一件事**就是 `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)`；判据要比 `客户区宽 / 逻辑宽 == 窗口DPI/96`，不能只比抓图尺寸 |
| 37 | **E2E 断言隐含硬件前提** | 拔掉副屏后「跨屏选区」用例 FAIL，看起来像代码坏了 | 跨屏断言先探 `EnumDisplayMonitors`：**不足 2 块屏就 SKIP**，并明确写「不是代码问题」 |
| 38 | **`serde_json` 不认 UTF-8 BOM** | 主题覆盖文件开头有 BOM → 解析失败 → 热重载静默不生效 | 写 JSON 用 `[System.IO.File]::WriteAllText($p, $json, (New-Object System.Text.UTF8Encoding($false)))`（**不带 BOM**） |
| 39 | **用户可填的数值直接进算法 → 卡死** | `long_screenshot_search`（i32，配置文件里无上限）直接当搜索距离循环，代价 `O(search × band × cols)` → 填个 999999 让长截图**永远转不完**；而且设置窗口的 `validate()` **连这个字段都没查** | **两道防线**：① UI 层字段访问器 `set_long_search()` 限范围（8~4000，见 `settings/form.rs`）；② core 层 `match_offset` 里 `search.clamp(0, MAX_SEARCH)` —— 外部调用方绕过 UI 也要安全 |
| 40 | **`Path::canonicalize()` 给的 `\\?\` 扩展长度前缀，WinRT 不认** | `StorageFile::GetFileFromPathAsync` 报 **`0x800700A1`**「指定的路径过长，超过了最大长度」—— 可路径只有 **60 个字符**，`%TEMP%` 也就 40 个字符。本地 OCR 100% 失败 | 给 WinRT 的绝对路径要**剥掉 `\\?\`**；UNC 形式 `\\?\UNC\server\share` 还原成 `\\server\share`。判别实验见 `screenloom-app/examples/ocr_probe.rs`（同一文件用两种路径各试一次） |
| 41 | **浮窗退出后残留的 `WM_QUIT` 会杀掉下一个消息循环** | 点工具栏「滚动截图」→ 提示窗**一帧都不显示**，长截图瞬间"完成"（只截到第一帧）。`--long` 命令行模式同样中招 —— 这条链路从来没真跑通过 | `finish()` 用 `PostQuitMessage` 退出，而事件循环是**先看到 `outcome.is_some()` 才 break** 的 → 那条 `WM_QUIT` 留在队列里，下一个 `GetMessageW` 立刻拿到它。退出前必须 `PeekMessageW(WM_QUIT, PM_REMOVE)` **只抽 WM_QUIT**（别把后台线程回投的 `WM_AI_REPLY` 一起吞掉） |
| 42 | **`WS_POPUP` 提示窗不会自动拿到键盘焦点** | 长截图提示窗显示正常，但按 `Enter` / `Esc` **毫无反应**，用户只能干瞪眼 | 浮窗刚退出、提示窗是新建的 `WS_POPUP`，Windows 不会把焦点给它。要显式 `SetForegroundWindow(hwnd)` + `SetFocus(Some(hwnd))`（`SetFocus` 在 `UI::Input::KeyboardAndMouse`，不在 `UI::WindowsAndMessaging`） |
| 43 | **`WS_CLIPCHILDREN` 不是窗口类样式** | 设置窗口直接起不来，`RegisterClassExW` 返回 0，只报「注册设置窗口类失败」，没有任何更具体的线索 | 它属于 **窗口样式**：`CreateWindowExW(..., WS_OVERLAPPEDWINDOW \| WS_CLIPCHILDREN, ...)`。`WNDCLASSEXW.style` 只接受 `CS_*`（`CS_HREDRAW` / `CS_VREDRAW` / `CS_DROPSHADOW` …），混入 `WS_*` 位 → `ERROR_INVALID_PARAMETER` |
| 44 | **滚动同步会把原生 `EDIT` 撑满自绘外框** | 输入框的圆角描边被盖住，四个角露出方角；创建时明明内缩过 | 创建与移动必须共用同一个 `edit_inner(frame, k)`：创建时按内缩矩形建，滚动时也把 `SetWindowPos` 的目标设成内缩矩形。只写在一处，另一处就会漂移 |
| 45 | **滚动后命中测试忘了加回偏移** | 滚过一段之后点复选框/下拉框没反应，或者点到了上一行的控件 | 鼠标坐标是客户区坐标，命中测试要换成内容坐标：`let cy = y + scroll.y;`，再用 `hit.contains(x, cy)`。绘制侧的 `-scroll.y` 和命中侧要成对出现 |
| 46 | **滚动时下拉菜单还开着 → 菜单浮在错误位置** | 菜单固定打开时的屏幕坐标，内容一滚就和控件错位 | 滚动入口统一走 `after_scroll()`：**先 `close_combo()` 再移位重绘**；`open_combo()` 用「内容坐标 - scroll.y」算屏幕位置 |

### C.2 命令行入口
