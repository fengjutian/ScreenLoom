# 编码进程隔离方案（P0-2）

> 状态：**设计待评审**（本文只定协议与改造边界，代码分三阶段落地）
> 目标：解决 [录屏方案.md](录屏方案.md) 风险 11 —— MF `SinkWriter` 偶发永久阻塞，目前只能把整个会话判死。
> 关联：[对标Cap与开源借鉴.md](对标Cap与开源借鉴.md) §6.1、[录屏功能需求.md](录屏功能需求.md) REC-67 / REC-102。

---

## 0. 结论

1. **必须隔离的是 `WriteSample` / `Flush` / `Finalize`，不只是 muxer**。阻塞点在 `IMFSinkWriter` 内部，只把封装搬走没有意义。
2. 因此子进程持**整个 SinkWriter**，父进程传 **NV12 帧**（共享内存），而不是传编码后样本（MF 不提供「编码器 / 封装器」拆分接口）。
3. 子进程卡死时，父进程 **kill + 等回收 + 用已落盘的 `.partial.mp4` 直接 remux**，当场产出可播文件；UI 全程不挂。
4. 控制通道用 **JSON lines over stdin/stdout**（复用现有 `serde_json`，零新增依赖），帧数据走**命名共享内存**。
5. 先在**影子模式**下与现有进程内编码并行验证，再切默认，最后做「卡死后续录」。

## 1. 问题与目标

### 1.1 现状

- 录制、BGRA→NV12、`WriteSample`、`Flush`、`Finalize` 全在 `screenloom-record-inner` 线程里。
- 看门狗（[session.rs](../screenloom-app/src/record/session.rs)）用 8 秒心跳停滞判定卡死，然后**中止整个会话**、保留 `.partial.mp4`。
- 实测（1080p，4 次）：Finalize 卡死 **3 次**，硬件/软件编码器都出现。卡死时用户当场拿不到正式文件。
- 已有缓解：partial 是 `FMPEG4`，可播；下次启动/下次开录自动 remux 成正式 MP4（[recovery.rs](../screenloom-app/src/record/recovery.rs)）。

### 1.2 目标

| 目标 | 判据 |
|---|---|
| UI 与录制线程不被阻塞 | 子进程卡死时，主进程 2 秒内可响应停止/退出的点击 |
| 当场产出可播文件 | kill 子进程后 ≤ 2 秒得到正式 MP4（remux），无需重启应用 |
| 不丢素材 | 已写入分片全部保留，帧数损失 ≤ 1 帧 |
| 可继续录 | （M3）kill 后自动起新子进程、写新分段，用户无感 |
| 性能不退化 | 1080p30 CPU 增量 ≤ 3%，帧延迟 ≤ 2 帧 |

### 1.3 非目标

- 不改帧节奏/时间戳策略（[pacer.rs](../screenloom-app/src/record/pacer.rs) 不动）。
- 不引入 FFmpeg 或任何外部二进制。
- 不把屏幕捕获搬进子进程（WGC 依赖窗口句柄与权限，留在父进程）。

## 2. 方案对比

| 方案 | 做法 | 能否解决卡死 | 结论 |
|---|---|---|---|
| A 现状 | 全部在进程内 | ❌ 只能整会话判死 | 保留为降级路径 |
| B muxer 子进程 | 父进程编码，子进程封装 | ❌ `WriteSample` 仍可能卡在父进程 | 否 |
| C 编码子进程 | 子进程持 SinkWriter，父进程传 NV12 | ✅ 可 kill、可重启 | **采用** |
| D 线程 + 调用超时 | 子线程写帧，超时放弃 | ❌ COM 调用不可取消，线程仍泄漏并占着文件 | 否 |

> Cap 的 `cap-muxer` 能传编码后样本，是因为它自研了编码与封装的分界；MF 的 `SinkWriter` 把两者绑在一起，所以只能传原始帧。

## 3. 架构

```text
UI 线程                 录制线程（父进程）                 编码子进程
──────                  ──────────────────                 ──────────
热键/托盘/HUD           取帧 → BGRA→NV12
   │                        │ 写共享内存槽
   │  PostMessage           │ send Frame{seq,slot,pts}
   │◄── 状态/统计 ──────────┤                              读槽 → WriteSample
   │                        │◄──── Ack{seq} / Stats ──────  SinkWriter(FMPEG4)
   │                        │                               .partial.mp4
   │                        │ send Stop → Stopped            Flush/Finalize
   ▼                        ▼                               （卡住也不影响父进程）
 收尾：remux partial → 正式 MP4
```

职责划分：

| 组件 | 职责 | 不做什么 |
|---|---|---|
| 录制线程 | 捕获、色彩转换、定速、投递帧、统计、看门狗 | 不碰 SinkWriter |
| 编码子进程 | 建 SinkWriter、写帧、Flush/Finalize、阶段上报 | 不捕获、不决定停止 |
| UI 线程 | 只读统计、发命令 | 不参与数据面 |

## 4. 进程与 IPC

### 4.1 进程启动

- 由 app 以 `CreateProcess`（`std::process::Command`）拉起同目录的 `screenloom-encoder-host.exe`。
- `stdin` 下发命令，`stdout` 上报事件；`stderr` 重定向到 `%TEMP%\screenloom-encoder.log`。
- 子进程命令行只带一个参数：共享内存名（或会话 id），其余全部走 `Init` 消息。
- 首次拉起失败（被杀毒拦截/文件缺失）→ 自动回退进程内编码，并**明确记录日志**。

### 4.2 共享内存

- 父进程创建：`Local\ScreenloomEnc-<pid>-<nonce>`，大小 = `SLOTS × frame_bytes`（`SLOTS = 3`）。
- 布局：`帧 0 | 帧 1 | 帧 2`，每槽 `frame_bytes = w*h*3/2`（NV12）。
- 子进程按名 `OpenFileMappingW` 映射，只读。
- **不传句柄**：命名映射天然跨进程，避免 `DuplicateHandle` 的权限与继承坑。

### 4.3 投递与流控

1. 父进程选一个空闲槽（子进程 `Ack` 后释放），`memcpy` 一帧 NV12，发 `Frame` 消息；
2. 子进程读槽、`WriteSample`、回 `Ack`；
3. 三个槽全在途时，**丢最旧帧**并计入 `dropped`（绝不阻塞录制线程）；
4. 子进程每 500ms 上报一次 `Stats`（已写帧数、编码耗时、阶段）。

> 3 槽 × 1080p NV12 ≈ 9.3 MB 共享内存，常驻开销可接受。

### 4.4 控制通道

- JSON lines（UTF-8，`\n` 分隔），每行一个对象。
- 父 → 子：`init`、`frame`、`stop`、`ping`、`abort`。
- 子 → 父：`ready`、`ack`、`stats`、`stopped`、`error`、`pong`。

## 5. 协议 v1

公共字段：`v`（协议版本）、`type`、`seq`。

| 方向 | 消息 | 字段 | 说明 |
|---|---|---|---|
| 父→子 | `init` | `w,h,fps,bitrate,path,shm,slots` | 建 SinkWriter；`path` 是 `.partial.mp4` 绝对路径 |
| 子→父 | `ready` | `frame_bytes` | 初始化成功 |
| 父→子 | `frame` | `seq,slot,pts,size` | 槽内是 NV12 |
| 子→父 | `ack` | `seq` | 槽可复用 |
| 子→父 | `stats` | `frames,encode_ms,stage` | `stage` ∈ write/flush/finalize |
| 父→子 | `stop` | — | 收尾：Flush → Finalize |
| 子→父 | `stopped` | `frames,bytes` | 正常收尾完成 |
| 父→子 | `ping` / 子→父 `pong` | `stage` | 心跳 |
| 子→父 | `error` | `code,msg` | 初始化/写帧/收尾失败 |

示例：

```json
{"v":1,"type":"init","w":1920,"h":1080,"fps":30,"bitrate":8000000,
 "path":"C:\\Users\\me\\Videos\\Screenloom\\2026-11-05.partial.mp4",
 "shm":"Local\\ScreenloomEnc-1234-ab12","slots":3}
{"v":1,"type":"frame","seq":42,"slot":1,"pts":14000000,"size":3110400}
{"v":1,"type":"ack","seq":42}
{"v":1,"type":"stats","frames":42,"encode_ms":7,"stage":"write"}
```

约定：

- `seq` 单调递增；父进程以 `ack` 判定槽释放，以 `stats` 判定存活；
- 父进程必须把 ack 记成**已确认帧数**（`seq + 1`），不能记"最后一个 ack 的 seq"：
  `seq 0` 既可能表示"还没 ack 过"，也表示"ack 过第 0 帧"，用 seq 表示无法区分，
  会把在途帧数少算一帧 —— 槽只有 3 个，少算一帧就可能在子进程还没取走旧帧时被覆盖；
- 版本不匹配 → 子进程回 `error{code:"version"}` 并退出，父进程回退进程内编码；
- 所有路径必须是绝对路径（MF 不接受 `file://`）。

## 6. 子进程内部

1. `CoInitializeEx(COINIT_MULTITHREADED)` → `MFStartup`；
2. `OpenFileMapping` 映射共享内存；
3. 按 `init` 建 `IMFSinkWriter`，容器 **`FMPEG4`**（与现状一致，保持崩溃可播）；
4. 逐帧 `WriteSample`，每帧/每 500ms 报 `stats`；
5. 收到 `stop`：`Flush` → `Finalize` → `stopped`；
6. 任何 `HRESULT` 失败：`error` 带 `HRESULT` 与原阶段，父进程据此决定是否重试；
7. 退出前 `MFShutdown`、关映射、关文件。

阶段标记复用现有 `Stage` 语义（write / flush / finalize），卡死时父进程能知道卡在哪一步。

## 7. 卡死检测与恢复

| 事件 | 父进程动作 |
|---|---|
| 1s 无 `pong` / `stats` | 标记可疑，继续等 |
| 3s 无心跳（可配 `SCREENLOOM_ENCODER_TIMEOUT_MS`） | `TerminateProcess` → 等回收 → **立即 remux partial → 正式 MP4** → 事件 `Failed("编码器无响应，已保存")` |
| 子进程崩溃（exit code ≠ 0） | 同上，错误信息带 exit code |
| 收尾阶段卡死 | 同样 kill；partial 已完整，remux 后直接交付 |
| 父进程崩溃 | 子进程失去 stdin → 读到 EOF 后自杀；partial 留给下次启动恢复 |

与现有看门狗的关系：

- 现在的 8 秒看门狗**保留**，作为「子进程管理线程本身也卡住」的最后防线；
- 正常情况下看门狗不再触发，因为它监控的心跳是子进程管理线程的，而该线程不会被 MF 阻塞。

> kill 后 partial 文件句柄由子进程持有；`TerminateProcess` 会由内核关闭句柄，父进程随后可读。

## 8. 失败语义矩阵

| 场景 | 用户看到 | 文件 |
|---|---|---|
| 正常停止 | 完成提示 + 打开文件夹 | 正式 MP4 |
| 子进程卡死 | 「编码器无响应，已保存已录内容」 | 正式 MP4（remux 自 partial） |
| 子进程崩溃 | 同上 + 错误码 | 正式 MP4 |
| remux 也失败 | 「已保留临时文件」 | `.partial.mp4`（可播） |
| 磁盘写满 | 提前停止 + 提示 | 已完成部分 remux |
| 拉起子进程失败 | 静默回退进程内编码，日志记录 | 正常 |

## 10. 分阶段

> **进展（2026-11-05，M2 已落地）**
>
> - `screenloom-encoder-protocol`（11 类消息 + 6 单测）、`screenloom-encoder-host`（子进程）、`record/encoder_client.rs`（父进程客户端）已落地；
> - **子进程成为默认**（M2）：`Encoder::new` 默认拉子进程，拉不起来自动回退进程内并打日志；`SCREENLOOM_ENCODER=inproc` 可强制进程内（排障用）；
> - **子进程就是父进程自己**：`screenloom.exe --encoder-host` 复用 `screenloom-encoder-host` 的库代码，不需要额外分发一个 exe —— 否则漏带二进制就会退化成进程内编码，等于白做；
> - 正常录制（子进程）：3 秒 → 50 帧 / 3.33 s，普通 MP4（`moov=1`、`moof=0`），结束后无残留子进程；
> - 注入 `SCREENLOOM_HOST_HANG=finalize`：Stop 后 4 秒判定无响应 → kill → remux → **当场交付可播 MP4**（实测 8.7 秒内出文件，50 帧 / 3.33 s），`.partial.mp4` 已消失；
> - 注入 `SCREENLOOM_HOST_HANG=write` + `SCREENLOOM_HOST_HANG_AFTER=30`（录到一半才卡）：杀掉子进程后已录内容照样救回（实测 28 帧 / 2.03 s 可播）；
> - 卡死率的实测基线：**进程内**路径 50 次采样卡死 3 次（≈6%，单次样本区间 3%~10%）；子进程路径不受影响（卡死变成 kill 子进程 + 救回）；
> - 卡死后走 `RecordEvent::Saved`：UI 弹「已录内容已保存」而不是「录屏失败」；CLI 按成功退出并打印保存路径；
> - 会话看门狗中止时调用 `kill_all_hosts()`，避免卡死的子进程变成孤儿；
> - 收尾失败时**不再调用 `Finalize`**（`Encoder::abandon`）：`Finalize` 卡死不可取消，再调一次会把整个线程挂死；
> - 编码器单测改为 `#[ignore]`（会触发 MF Finalize 偶发阻塞，见风险 11），用 `cargo test -- --ignored` 手动跑。
>
> 自动化验收：[scripts/e2e_encoder_host.ps1](../scripts/e2e_encoder_host.ps1)（已接入 `scripts/verify_all.ps1`）——
> A 子进程正常录制 / B 注入卡死后当场拿到可播 MP4 / C 子进程不可用自动回退 / D 无残留子进程，四项判据均可由第三方复核。
>
> 剩余：影子模式对比（M1 的量化数据）、连续 50 次稳定性与 CPU 预算实测。

### M1 · 影子模式（对用户无影响）

- 录制时同时开子进程，帧投递给子进程，但**仍以进程内编码的结果为准**；
- 只记录：子进程延迟、丢帧、失败率、与进程内产物的帧数差；
- 判据：连续 20 次录制，子进程路径与进程内路径帧数一致（±1）；1080p30 增量 CPU ≤ 3%。

### M2 · 默认子进程

- 子进程成为默认，失败自动回退；
- 卡死 → kill → remux → 交付，全程 UI 可操作；
- 判据：注入 10 秒 Finalize 阻塞，kill 后 2 秒内产出可播 MP4；连续 50 次录制零坏文件。

### M3 · 卡死续录（可选）

- kill 后用新子进程写新分段，停止时合并；用户只看到一个文件；
- 依赖 M2 与分片 manifest（分段落盘已在 [paths.rs](../screenloom-app/src/record/paths.rs) 有基础）。

## 11. 风险

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| 1 | 共享内存名冲突 / 权限 | 子进程打不开映射 | 名字带 pid + nonce；失败即回退 |
| 2 | 子进程被 EDR/杀软拦截 | 拉不起来 | 自动回退进程内；日志提示 |
| 3 | 跨进程帧拷贝开销 | CPU 上升 | 1080p NV12 93MB/s，memcpy 占比很低；1080p60 实测再定 |
| 4 | 子进程 stderr 丢失导致难排查 | 调试成本 | 落文件 + 父进程日志带 session id |
| 5 | 子进程里 MF 行为与进程内不同（GPU 编码器选择） | 性能差异 | M1 影子模式对比码率/帧率/CPU |
| 6 | 父进程崩溃时子进程成孤儿 | 残留进程 | 子进程检测 stdin EOF 后自杀；父进程退出前显式 kill |
| 7 | 双份代码（进程内/子进程）维护成本 | 长期负担 | 进程内实现仅作降级，M4 后考虑删除 |

## 13. 待决策

| 议题 | 选项 | 建议 |
|---|---|---|
| 帧槽数 | 2 / 3 / 4 | **3**（延迟与内存平衡） |
| 心跳超时 | 2s / 3s / 5s | **3s**（Finalize 正常可能 > 1s） |
| 控制协议 | JSON lines / 二进制 | **JSON**（复用 serde_json，可读、可抓包） |
| 子进程粒度 | 每次录制一个 / 常驻 | **每次录制一个**（状态简单，启动 ~50ms） |
| 回退策略 | 静默 / 提示 | **静默 + 日志**（录制优先） |
